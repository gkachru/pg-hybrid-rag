# Use BM25 ranking for the full-text leg

This guide shows how to replace the default tsvector full-text leg with BM25 ranking from the pg_textsearch extension, and how the BM25 leg routes queries to per-language indexes. The vector and keyword legs are unchanged.

BM25 changes ranking quality in ways that depend on your corpus and languages. Measure it on your own queries before you enable it broadly; see [Tune relevance](/how-to/tune-relevance).

## Before you begin

- Install pg_textsearch, add it to `shared_preload_libraries`, and restart Postgres. See [Prepare PostgreSQL](/how-to/prepare-postgres). The example Docker image ships pg_textsearch 1.5.1.
- Apply the base migrations with `ragMigrate`. The BM25 indexes cover `content_normalized`, which `RagIndexer` always writes.

## Apply the BM25 migrations

```ts
import { ragMigrate, type TransactionProvider } from "pg-hybrid-rag";

// Both come from "Run migrations": the package's sql/ directory and a pinned,
// non-transactional provider connected as the schema owner.
declare const sqlDir: string;
declare const migrationProvider: TransactionProvider;

// Pass the same flags you used before, plus this one.
await ragMigrate(migrationProvider, { sqlDir, bm25: true });
```

Passing `sqlDir` works in every version; 0.2.5 and earlier require it when the library is installed as a package. See [Run migrations](/how-to/run-migrations).

This applies migration 011, which creates the `pg_textsearch` extension and one partial BM25 index per language group, and migration 015, which rebuilds those indexes on `content_normalized`. The tsvector column and its trigger stay in place, so both strategies keep working.

Building the indexes reads every existing row. On a large table, run the migration in a maintenance window.

## Switch the FTS strategy

Pass `Bm25Fts` as the adapter's `fts` option. It combines with the other adapter options.

```ts
import { Bm25Fts, PostgresRagDatabase, RagPipeline } from "pg-hybrid-rag";

const db = new PostgresRagDatabase(txProvider, { fts: new Bm25Fts() });
const pipeline = new RagPipeline({ tenantId, db, embedder });
```

## Search with the right language

`Bm25Fts` uses the query `language` to pick the index and to restrict the leg to that index's languages:

| Index | Document languages | Stemming |
| --- | --- | --- |
| `idx_rag_bm25_en` | `en`, `en-US`, `en-IN` | english |
| `idx_rag_bm25_es` | `es`, `es-ES`, `es-MX` | spanish |
| `idx_rag_bm25_fr` | `fr`, `fr-FR` | french |
| `idx_rag_bm25_de` | `de`, `de-DE` | german |
| `idx_rag_bm25_it` | `it`, `it-IT` | italian |
| `idx_rag_bm25_pt` | `pt`, `pt-PT` | portuguese |
| `idx_rag_bm25_ro` | `ro`, `ro-RO` | romanian |
| `idx_rag_bm25_simple` | every other code, including unlisted variants such as `en-GB` or `pt-BR` | none (`simple`) |

```ts
await pipeline.search("running shoes", { language: "en" }); // idx_rag_bm25_en, English documents only
await pipeline.search("chaussures de course", { language: "fr" }); // idx_rag_bm25_fr, French documents only
await pipeline.search("जूते", { language: "hi" }); // idx_rag_bm25_simple, all documents outside the stemmed groups
```

Consequences to plan for:

- The BM25 leg never returns a document from another language group. A query with `language: "en"` gets no BM25 hits from Spanish documents, even when you omit `languages`. The vector and keyword legs still search across languages.
- Codes outside the groups share the `simple` index, unstemmed. That includes `ar`, which the tsvector strategy does stem with Postgres's `arabic` config.
- The groups are fixed in the library. A stemmer you add to `rag_fts_config` (see [Search across languages](/how-to/multilingual-search#add-a-stemmer-for-a-new-language)) does not reach the BM25 leg.

## How BM25 queries are built

The leg sends the lexical query as a list of terms, after stop-word removal. Synonyms are added as extra terms, without the phrase and OR structure the tsvector strategy builds. Documents that share no term with the query score `0` and are dropped, so only real lexical matches enter fusion.

## Switch back

Construct the adapter without `fts`, or pass `new TsvectorFts()`:

```ts
import { PostgresRagDatabase, TsvectorFts } from "pg-hybrid-rag";

const db = new PostgresRagDatabase(txProvider, { fts: new TsvectorFts() });
```

The tsvector column is kept current by its trigger, so switching back needs no re-index. The BM25 indexes remain and are still updated on every write. If you stop using BM25 for good, you can drop them. `ragMigrate` does not recreate them later, because migrations 011 and 015 stay recorded as applied in `_rag_migrations`.

## Gotchas

- If the extension is not preloaded or the indexes are missing, the FTS leg fails, and a failed leg fails the whole search.
- Pass the query `language` you actually mean. `search()` requires it, and with BM25 it also decides which documents the full-text leg can see.
- BM25 and the tsvector strategy both apply attribute filters, `sourceTypes`, `sourceIds` and `languages`.
